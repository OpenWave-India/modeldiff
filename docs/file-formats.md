# File formats

ModelDiff reads test suites and run configurations, can replay recorded outputs, writes run-result JSON, and produces comparison JSON. This page documents the formats implemented by the source code.

The source of truth for suite fields is `src/modeldiff/cases.py`; configuration fields are defined in `src/modeldiff/config.py`; replayed outputs are read by `src/modeldiff/providers.py`; run results are defined in `src/modeldiff/results.py`; and comparison data is produced by `src/modeldiff/compare.py`.

## Compatibility and validation

- Suite and configuration files may use JSON or YAML (`.json`, `.yaml`, or `.yml`).
- Suite and configuration schemas reject unknown fields. Add only fields supported by the version of ModelDiff being used.
- Run-result files identify their format with `modeldiff.run/v1`. The reader validates the documented schema, which permits additional properties. Unknown top-level and per-case properties are not passed into the corresponding dataclass fields; the `config` object is retained as a dictionary. Acceptance of extra properties does not guarantee that every future format change will be backward-compatible.
- Comparison JSON identifies its format with `modeldiff.comparison/v1`. It is the serialized output of a comparison, not a run-result file.
- Unless a field is explicitly required, it is optional in the input schema. Defaults described below are applied by the implementation where stated.
- Examples referencing `examples/quickstart/` use the repository's checked-in fixtures. The quickstart recorded outputs are hand-written examples, not outputs generated by a real model.

## 1. Test suite file

A suite defines a named collection of cases. A suite can be written in YAML or JSON.

### Top-level fields

| Field | Type | Required? | Meaning |
| --- | --- | --- | --- |
| `suite` | string | Yes | Name of the suite. Must not be empty. |
| `cases` | array of case objects | Yes | Cases to validate and run. The loader rejects an empty cases array, although the JSON schema itself does not specify a minimum length. |
| `description` | string | No | Human-readable description. Defaults to an empty string when loaded if omitted. |

Unknown top-level fields are rejected.

### Case fields

Every item in `cases` must be an object with these required fields:

| Field | Type | Required? | Meaning |
| --- | --- | --- | --- |
| `id` | string | Yes | Unique case identifier. Must start with a letter or digit; remaining characters may be letters, digits, `.`, `_`, or `-`. Duplicate IDs are rejected. |
| `type` | string enum | Yes | Check type. Allowed values: `exact`, `json`, `classification`, `required_fields`, `tool_call`, `custom`. |
| `input` | string | Yes | Input prompt supplied to the provider. |

Optional case fields:

| Field | Type | Required? | Meaning |
| --- | --- | --- | --- |
| `expected` | any JSON/YAML value | No | Expected value used by the selected check type. Its precise interpretation depends on the check. |
| `schema` | object | No | JSON Schema used by checks that support a schema, such as `json`. |
| `labels` | array of strings | No | Allowed labels for classification checks. If supplied, the array must contain at least one item. |
| `required` | array of non-empty strings | No | Required field paths for `required_fields` checks. |
| `values` | object | No | Mapping of field paths to expected values for `required_fields` checks. |
| `check` | non-empty string | No | Name of the registered custom check for a `custom` case. |
| `params` | object | No | Parameters passed to a custom check. Defaults to an empty object. |
| `options` | object | No | Options used by supported checks. Defaults to an empty object. |
| `tags` | array of strings | No | Labels used to organize or select cases. Defaults to an empty array. |
| `metadata` | object | No | User-supplied metadata. Defaults to an empty object; it is not interpreted as a check by itself. |
| `generation` | object | No | Generation options passed to the provider. For Ollama, case-level generation settings override the configuration's options. Defaults to an empty object. |
| `performance` | object | No | Performance constraints. Currently supports `max_latency_ms`, a number greater than zero. Unknown keys inside this object are rejected. |

Unknown case fields are rejected. Additional semantic validation may apply depending on the case type; see `src/modeldiff/checks.py`.

### Case types and type-specific fields

| Type | Main fields | Purpose |
| --- | --- | --- |
| `exact` | `expected` | Checks whether output matches the expected text, subject to supported options. |
| `json` | `schema` | Checks whether output is valid JSON and, when provided, conforms to the schema. |
| `classification` | `expected`, optional `labels` | Checks the predicted classification label. |
| `required_fields` | `required`, optional `values` | Checks required field paths and expected values in structured output. |
| `tool_call` | `expected` | Checks a tool-call representation, including the expected tool name and any configured arguments or argument schema. |
| `custom` | `check`, optional `params` | Runs a registered custom check. |

The meaning and validation of these fields are determined by the corresponding check implementation. Do not assume that every optional field is meaningful for every case type.

### Quickstart example

This excerpt follows the checked-in `examples/quickstart/suite.yaml` fixture:

```yaml
suite: support-assistant
description: Example regression suite for a customer-support assistant.

cases:
  - id: greeting-exact
    type: exact
    input: "Reply with exactly: Hello! How can I help you today?"
    expected: "Hello! How can I help you today?"
    tags: [smoke]

  - id: sentiment-positive
    type: classification
    input: "Classify the sentiment: 'Support fixed it in five minutes!'"
    expected: positive
    labels: [positive, neutral, negative]
    tags: [classification]
```

The complete example suite includes all six case types. Its recorded outputs are fixtures illustrating possible results; they are not claimed to come from a real model.

### Suite hash

ModelDiff calculates `suite_sha256` from normalized case definitions. It serializes the cases with sorted JSON keys and compact separators, then computes SHA-256 over the UTF-8 bytes. Formatting and comments in the source YAML/JSON do not affect this hash. The hash is used to check whether two runs used the same case definitions.

## 2. Run configuration file

A configuration describes one side of a comparison and selects the provider used to produce outputs.

### Fields

| Field | Type | Required? | Meaning |
| --- | --- | --- | --- |
| `id` | string | Yes | Identifier for this run configuration. Must start with a letter or digit; remaining characters may be letters, digits, `.`, `_`, `:`, or `-`. |
| `provider` | string enum | Yes | Provider to use: `replay` or `ollama`. |
| `description` | string | No | Human-readable description. |
| `capture_output` | string enum | No | Output capture mode: `full`, `hash`, or `none`. Defaults to `full`. |
| `metadata` | object | No | User-supplied metadata. |
| `outputs` | non-empty string | Conditional | Path to the recorded-output file. Required when `provider` is `replay`. |
| `model` | non-empty string | Conditional | Ollama model name. Required when `provider` is `ollama`. |
| `base_url` | string | No | Ollama server URL. Must begin with `http://` or `https://`. |
| `options` | object | No | Ollama generation options. |
| `format` | any value | No | Optional format value passed to Ollama. |
| `system` | string | No | Optional system prompt passed to Ollama. |
| `timeout_s` | number greater than zero | No | Ollama request timeout in seconds. |

Unknown configuration fields are rejected. The configuration schema requires `outputs` for replay and `model` for Ollama. Other Ollama settings are optional.

Paths for recorded outputs are resolved relative to the configuration file's directory.

### Quickstart example

From `examples/quickstart/configs/baseline.yaml`:

```yaml
id: baseline-q8
provider: replay
outputs: ../recorded/baseline.json
capture_output: full
metadata:
  description: Outputs recorded before the change.
```

The corresponding candidate fixture uses `id: candidate-q4` and points to `../recorded/candidate.json`.

### Output capture and privacy

| Mode | Stored output data | Can compare output changes? |
| --- | --- | --- |
| `full` | Output text and SHA-256 hash | Yes |
| `hash` | SHA-256 hash without output text | Yes, but the text of the change is unavailable |
| `none` | Neither output text nor its hash | No; output changes may be unknown |

Pass/fail evaluation is performed on the full output in memory, regardless of the capture mode.

When recording configuration details in a result file, ModelDiff redacts values whose keys match patterns for API keys, tokens, secrets, passwords, or authorization. Review result files before sharing them, because prompts, failure reasons, and other metadata may still contain sensitive information.

## 3. Recorded-output file

The `replay` provider reads a JSON file containing an `outputs` object. Each key is a case ID. Its value is either a plain output string or an object containing output text and optional metadata.

### Fields

| Field | Type | Required? | Meaning |
| --- | --- | --- | --- |
| `outputs` | object | Yes | Maps case IDs to recorded outputs. |
| `metadata` | object | No | Optional provider-level metadata. If the value is not an object, the replay provider ignores it and uses an empty object. |

Each entry under `outputs` may be:

| Entry field or shape | Type | Required? | Meaning |
| --- | --- | --- | --- |
| Plain entry | string | Yes, as an alternative | The recorded output text for that case. |
| `output` | string | Yes, for an object entry | Recorded output text. |
| `latency_ms` | number greater than or equal to zero | No | Recorded latency in milliseconds. |
| `metadata` | object | No | Per-output provider metadata. Defaults to an empty object when omitted. |

An object entry must contain a string `output`. If `latency_ms` is supplied, it must be a non-negative number. The replay provider reports a missing case output as a provider error during execution. The reader does not require every suite case to be present when it loads the file.

### Quickstart example

This excerpt is based on `examples/quickstart/recorded/baseline.json`:

```json
{
  "metadata": {
    "note": "Hand-written fixture outputs for the quickstart. Not produced by a real model."
  },
  "outputs": {
    "greeting-exact": {
      "output": "Hello! How can I help you today?",
      "latency_ms": 310
    },
    "sentiment-positive": {
      "output": "neutral",
      "latency_ms": 155
    }
  }
}
```

If `latency_ms` is supplied, ModelDiff uses that recorded value and sets `duration_source` to `recorded`. If it is omitted, the provider call is timed by ModelDiff and the source is `measured`.

## 4. Run-result JSON

A run writes a JSON object identified by:

```json
{
  "format": "modeldiff.run/v1"
}
```

The run-result schema is defined by `RESULT_SCHEMA` in `src/modeldiff/results.py`. The top-level object must contain `format`, `suite`, `suite_sha256`, `config`, `started_at`, and `results`.

### Top-level fields

| Field | Type | Required? | Meaning |
| --- | --- | --- | --- |
| `format` | string constant | Yes | Must be `modeldiff.run/v1`. Identifies the run-result format. |
| `suite` | string | Yes | Name of the suite that was run. |
| `suite_sha256` | string | Yes | Lowercase, 64-character hexadecimal SHA-256 hash of normalized case definitions. |
| `config` | object | Yes | Public configuration details. Must contain string fields `id` and `provider`. |
| `started_at` | string | Yes | Run start timestamp. |
| `results` | array of case-result objects | Yes | Result record for each executed case. |
| `capture_output` | string enum | No | `full`, `hash`, or `none`; defaults to `full` in a `RunResult`. |
| `runtime` | object | No | Runtime metadata, such as environment and provider details. Defaults to an empty object. |
| `finished_at` | string or null | No | Run finish timestamp. Defaults to null. |
| `unavailable_metrics` | array of strings | No | Metrics unavailable during the run. Defaults to an empty array. |

The config object's schema requires `id` and `provider`, both strings. The implementation may record other public configuration properties as well.

### Per-case result fields

Every item in `results` is an object with these required fields:

| Field | Type | Required? | Meaning |
| --- | --- | --- | --- |
| `case_id` | string | Yes | ID of the test case. Duplicate case IDs in one run result are rejected. |
| `type` | string | Yes | Case type. |
| `status` | string enum | Yes | `pass`, `fail`, or `error`. |
| `timestamp` | string | Yes | Timestamp associated with this case result. |

Optional case-result fields:

| Field | Type | Required? | Meaning |
| --- | --- | --- | --- |
| `reason` | string or null | No | Explanation of the check result, when available. |
| `output` | string or null | No | Captured output text. May be null or absent depending on capture mode. |
| `output_sha256` | string or null | No | SHA-256 hash of the output when captured. |
| `duration_ms` | number or null | No | Duration in milliseconds; if numeric, must be non-negative. |
| `duration_source` | `measured`, `recorded`, or null | No | Whether duration was measured around the provider call or supplied by a recorded-output entry. |
| `memory` | object or null | No | Memory measurements when available. |
| `details` | object | No | Structured details from the check, such as classification information. Defaults to an empty object in `CaseResult`. |
| `warnings` | array of strings | No | Non-fatal warnings. Defaults to an empty array. |
| `error` | string or null | No | Error information when execution or evaluation errors. |
| `provider_metadata` | object | No | Metadata returned by the provider. Defaults to an empty object. |
| `tags` | array of strings | No | Tags associated with the case. Defaults to an empty array. |

The reader validates the documented types and required fields. The `CaseResult` and `RunResult` constructors also define defaults for optional values; see their dataclasses in `src/modeldiff/results.py`.

### Meaning of `status`

- `pass`: the case's check passed.
- `fail`: the output was evaluated, but the check did not pass.
- `error`: the case could not be evaluated normally because an error occurred, for example a provider or custom-check error.

A failure is not the same as an execution error. Comparisons treat both `fail` and `error` as non-passing statuses when categorizing regressions and fixes.

### Meaning of `duration_source`

- `recorded`: the duration came from `latency_ms` in a replay entry.
- `measured`: ModelDiff measured the provider call duration.
- `null`: no duration source is available.

A numeric `duration_ms` is not by itself enough to tell whether it was measured or recorded; inspect `duration_source`. Comparisons also report the sources used by the two runs so that different measurement methods are visible.

### Example case-result object

This example shows the documented shape. Values such as timestamps and hashes are illustrative:

```json
{
  "case_id": "greeting-exact",
  "type": "exact",
  "status": "pass",
  "timestamp": "2026-10-29T10:00:00+00:00",
  "reason": null,
  "output": "Hello! How can I help you today?",
  "output_sha256": "fda564ba3f7a0f028106d468420f674898ed99ac5bf2765ac9586206e39d73c5",
  "duration_ms": 310.0,
  "duration_source": "recorded",
  "memory": null,
  "details": {},
  "warnings": [],
  "error": null,
  "provider_metadata": {},
  "tags": ["smoke"]
}
```

The object above illustrates the field layout; it is not presented as a verbatim captured run-result file. The checked-in quickstart recorded-output fixtures are explicitly hand-written and are not real model outputs.

## 5. Comparison JSON

Comparison JSON is produced when comparing a baseline run with a candidate run. Its format identifier is `modeldiff.comparison/v1`. It contains an ordered list of per-case comparisons, summary counts, and optional latency information.

### Top-level fields

| Field | Type | Required in serialized output? | Meaning |
| --- | --- | --- | --- |
| `format` | string constant | Yes | `modeldiff.comparison/v1`. |
| `suite` | string | Yes | Suite name shared by the compared runs. |
| `baseline_id` | string | Yes | Baseline run configuration ID. |
| `candidate_id` | string | Yes | Candidate run configuration ID. |
| `cases` | array of comparison objects | Yes | Per-case comparison records. |
| `latency` | object or null | Yes in serialized output | Latency summary when comparable duration values exist; otherwise null. |
| `latency_threshold_pct` | number or null | Yes in serialized output | Percentage threshold used for slowdown flagging, if configured. |
| `suite_mismatch` | boolean | Yes | Whether the suite hashes differed. |
| `notes` | array of strings | Yes | Explanatory notes, including relevant compatibility or measurement warnings. |
| `summary` | object | Yes | Counts for comparison categories and other change indicators. Added by `Comparison.to_dict()`. |

The `Comparison` object is converted to a dictionary by `Comparison.to_dict()`. That method adds the `format` and `summary` fields, adds `duration_delta_ms` to each case, converts a non-null `label_change` tuple to an object, and adds `change_pct` to a non-null latency summary.

### Comparison categories

The `category` field of each case has one of these values:

| Category | Meaning |
| --- | --- |
| `regression` | Baseline passed, but the candidate failed or errored. |
| `fixed` | Baseline failed or errored, and the candidate passed. |
| `still_failing` | Both baseline and candidate have non-passing statuses. |
| `unchanged_pass` | Both baseline and candidate passed. Output may still have changed. |
| `missing_in_candidate` | The case exists in the baseline results but not in the candidate results. |
| `missing_in_baseline` | The case exists in the candidate results but not in the baseline results. |

An output change is not automatically a regression. A case can be `unchanged_pass` while its output differs, because the case's check still passed. Only `regression` cases count as regressions in the comparison logic.

### Per-case comparison fields

| Field | Type | Meaning |
| --- | --- | --- |
| `case_id` | string | Case identifier. |
| `type` | string | Case type. |
| `category` | string | One of the six categories above. |
| `baseline_status` | string or null | Baseline status, or null if missing from the baseline. |
| `candidate_status` | string or null | Candidate status, or null if missing from the candidate. |
| `baseline_reason` | string or null | Baseline reason, falling back to its error message when needed. |
| `candidate_reason` | string or null | Candidate reason, falling back to its error message when needed. |
| `output_changed` | boolean or null | Whether output changed. Null means the change could not be determined from captured output or hashes. |
| `label_change` | object or null | When a predicted classification label changed, an object with `from` and `to` values. |
| `baseline_duration_ms` | number or null | Baseline duration in milliseconds. |
| `candidate_duration_ms` | number or null | Candidate duration in milliseconds. |
| `slowdown` | boolean | Whether the case met the configured slowdown conditions. |
| `duration_delta_ms` | number or null | Candidate duration minus baseline duration. Added during serialization. |

The `label_change` object is derived from `details.predicted_label` in both case results. It is null when no such change is detected.

### Latency summary

When there are cases with duration values in both runs, the serialized `latency` object contains:

| Field | Type | Meaning |
| --- | --- | --- |
| `cases` | integer | Number of cases with duration values on both sides. |
| `baseline_median_ms` | number | Median baseline duration for those cases. |
| `candidate_median_ms` | number | Median candidate duration for those cases. |
| `baseline_sources` | array of strings | Non-null duration sources found in the baseline run. |
| `candidate_sources` | array of strings | Non-null duration sources found in the candidate run. |
| `change_pct` | number or null | Percentage change between candidate and baseline medians. Null when the baseline median is zero. |

Slowdown flags are reported separately from regression categories. A case is flagged only when its percentage increase exceeds `latency_threshold_pct` and its duration increase is at least `min_latency_delta_ms`. Different duration sources may make a latency comparison less directly comparable; the comparison notes this when source sets differ.

### Summary fields

The `summary` object includes:

- One count for each category: `regression`, `fixed`, `still_failing`, `unchanged_pass`, `missing_in_candidate`, and `missing_in_baseline`.
- `output_changed`: count of cases whose `output_changed` value is truthy.
- `behavior_changes`: count of `unchanged_pass` cases with changed output.
- `label_changes`: count of cases with a non-null label change.
- `slowdowns`: count of cases flagged as slowdowns.

### Comparison compatibility checks

By default, ModelDiff refuses to compare runs with different suite names or different `suite_sha256` values. A suite-hash mismatch can be allowed with the CLI's `--allow-suite-mismatch` option, but the comparison includes a note because the case definitions may not be equivalent. Cases present on only one side are represented using the corresponding missing category.
